# /pipeline-estimate — 4단계: 비용·기술 산정

## 공통 계약 (요약 — 정본은 `.claude/commands/_CONTRACT.md`, 충돌 시 정본 우선)

1. 시작: `pipeline.json` 읽기 → `stage`가 `"estimate"`인지 확인(아니면 쓰지 말고 보고 후 종료) →
   `stageStatus: "running"` 기록. 쓰는 필드는 `stage`/`stageStatus`/`artifacts`만, 나머지는 보존,
   항상 ① Write 도구로 `<대상>.tmp` 작성 ② `bash .claude/atomic-mv.sh <대상>.tmp <대상>`으로
   교체(원자적). `stage` 값은 바꾸지 않는다.
2. 산출물은 `templates/ESTIMATE.template.md`의 고정 블록(메타 + §1~§7, 총 8블록) 구조 그대로
   유지한다(추가·삭제 금지, 해당 없으면 "해당 없음"+이유). 완료 시 `artifacts`에 등록.
3. 종료 시 `stageStatus`는 `"awaiting_confirm"` 또는 `"awaiting_feedback"` — **`running`인 채 종료
   금지**(그대로 종료하면 host가 `error`로 강등해 사용자에게 실패로 보인다).
4. `피드백:` 접두 호출 = 기존 산출물 수정 모드(조정 회차 증가). "그냥 질문"이면 순변경 없이 답만
   하고 실행 전 상태를 복원.
5. 이 단계는 기능 가감 조정 자체가 범위 **안**이다(그래서 estimate가 PRD를 직접 고친다 — 아래
   "PRD 갱신" 참조). 범위 밖은 "지금 바로 개발 시작해줘"처럼 다음 단계 진입을 요구하는 경우뿐이며,
   이때는 산출물을 바꾸지 말고 "컨펌하면 5단계(개발)로 진행합니다"라고 안내만 한다.
6. 보안: 자격증명(anon key/service key 등)을 문서·로그에 하드코딩하지 않고 `.env.example` 형식
   안내로만 남긴다 · 프로젝트 디렉터리 밖 파일 생성 금지 · 이 단계는 웹 도구를 쓰지 않으므로
   신뢰불가 웹 입력은 해당 없음.

`artifacts`에는 이 단계 소유 키 **`estimate`만** 추가·갱신하고 기존 키(`ideas`, `prd`, `mockup` 등)는
전부 보존한다. `guardrails` 키는 이 단계가 아니라 5단계(개발) 완료 시점의 소관이다 — estimate는
`COST-GUARDRAILS.md` **파일을 만들지 않는다**(아래 "가드레일 적용 여부" 참조).

## §1 백엔드 판정 (비즈니스 모델 단계 결정을 소비)

`BUSINESS.md`(3단계 산출물, artifacts.business)가 있으면 **그 §2 백엔드 판정·§3 0원 게이트를 그대로
소비한다 — 이 단계는 백엔드 필요 여부를 재판정하지 않는다.** 판정값(로컬/정적/백엔드)과 근거로
"BUSINESS.md §2"를 §1에 적는다. 두 경우로 나뉜다:

- **게이트 "통과"**(로컬·정적·광고만): §1을 그 값으로 확정하고 아래 ①②③ 트리 절차는 건너뛴다.
  백엔드 채택(BUSINESS.md §2가 서버)인데 게이트가 통과인 경우는 없다(서버=유보). 
- **게이트 "유보"**(구독·서버를 골랐지만 나중에 연동): v1은 백엔드를 실제로 붙이지 않고 스텁으로
  가므로, §1을 **"백엔드 필요하나 v1 보류(스텁) — 나중에 연동"**으로 적는다. 이 경우 §2~§4 비용은
  "해당 없음(v1은 서버 미연동)"으로 처리하고, `BUSINESS.md` §4의 나중에 연동 TODO 목록을 §5 개발
  범위 요약에 옮긴다(개발 단계가 스텁으로 남길 근거).

`BUSINESS.md`가 없으면(구 프로젝트) `docs/PRD.md` §3(기능 목록)·§5(데이터 모델)·§8(백엔드 결정 트리
예비 판정)을 읽고, **반드시 ①→②→③ 순서로** 직접 최종 판정한다(PRD §8은 예비 판정):

1. **① 로컬**: 이 앱의 기능이 기기 로컬 저장(SharedPreferences, sqlite 등)만으로 되는가? 예이면
   여기서 확정 — 백엔드 없음. 근거를 명시한다(예: "모든 데이터가 사용자 1인 기기 안에서만 의미
   있음, 서버 동기화 요구 없음").
2. **② 정적/번들**: (①이 아니오일 때만) 서버가 필요해 보여도 정적 데이터 번들·정적 호스팅으로
   대체 가능한가? 예이면 여기서 확정. ①에서 확정됐으면 이 칸은 "해당 없음(①에서 확정)"으로
   적어 검토했음을 남긴다(건너뛴 게 아니라 판단한 것).
3. **③ 백엔드**: (②도 아니오일 때만) 진짜 사용자 간 공유·동기화가 필요한가? 예이면 백엔드
   채택 — 이때 그 기능이 PRD §6 수익화 계획을 정당화하는지 함께 명시한다(순수 비용만 늘리는
   백엔드 채택은 근거 부족으로 취급).
4. 백엔드 채택 시 **기본 스택은 Supabase**(RLS·인증·anon/service key 분리 — PRD §5 데이터 모델을
   SQL 마이그레이션 대상으로 삼는다). Firebase는 Supabase로 해결 어려운 특정 요건(예: RTDB 기반
   실시간 version-check)에만 대안으로 채택하고 그 근거를 §1과 §6에 남긴다.
5. **PRD §8과의 정합성**: 이 단계의 최종 판정이 PRD §8의 예비 판정과 다르면(예: 예비는 로컬이었으나
   실제로는 백엔드가 필요하다고 판단), PRD §8을 이 최종 값으로 갱신하고 §7 PRD diff 요약에
   반영한다(아래 "PRD 갱신" 절차를 따른다) — ESTIMATE.md §1과 PRD §8은 항상 같은 값이어야 한다.

## §2~§4 (백엔드 채택 시에만 실질 작성)

- **§2 기능→서비스 매핑 표**: PRD §3 기능마다 필요 서비스(인증/DB/스토리지/광고/없음(로컬))와
  스택·플러그인을 적는다. 백엔드 미채택이면 모든 행의 "필요 서비스"를 "없음(로컬)"로 채우고
  표 자체는 유지한다.
- **§3 비용 리스크 표 — 산식 강제**: 백엔드 미채택이면 섹션 전체를 "해당 없음 — 로컬 완결형,
  서버 운영비 없음"으로 표기(표는 헤더까지 유지, 삭제 금지). 백엔드 채택 시에는 각 행을
  **반드시** "행동 × 빈도 × DAU = 일일 호출량" 산식 + 무료 티어 대비 배율/초과 여부로 적는다
  (형식 예: "피드 열 때마다 Firestore read 30건 × DAU 1천 × 10회/일 = 30만 read/일 → 무료
  티어(5만/일) 6배 초과"). "비용이 늘 수 있다" 같은 정성적 서술만 적는 것은 금지. 완화책 열에는
  `COST-GUARDRAILS.md`의 해당 체크리스트 항목을 인용하고, **완화 후 예상치** 열을 반드시 함께
  채운다(완화책만 적고 수치를 비워두지 않는다).
- **§4 MAU 시나리오**: 백엔드 미채택이면 "해당 없음 — 서버 운영비 없음". 채택 시 무료 티어(초기) /
  1천 MAU / 1만 MAU **최소 3개 시나리오**를 표로 남긴다(무료 티어 초과 여부·예상 월 비용·근거).

## §5 개발 범위 요약 + 목업 재동기화 판단

이번 조정으로 기능을 뺐다면(WON'T v1 이동) 무엇을·왜, 넣었다면 무엇을·왜 적는다. 그리고 이 조정이
**PRD §4 화면 목록(화면 ID 추가/삭제/역할 변경)에 영향을 줬는지** 판단해 "목업 롤백 필요 여부"
칸에 명시한다:

- 영향 없음 → "필요 없음(화면 변화 없음)".
- 영향 있음 → "필요 — 영향받은 화면: `<화면ID, ...>`(해당 화면만 재생성·재컨펌, 나머지 화면은
  기존 목업 유지)". 화면 ID 대조는 **이 조정으로 갱신된 PRD**가 기준이다(§2-4 재동기화 규칙) —
  롤백을 실제로 트리거하는 것은 사용자 몫이며, 이 스킬은 갱신된 PRD를 반영하고 권고 문구를
  §5와 채팅 보고에 남기는 데까지만 책임진다.

## §6 권장 구성

런타임/서비스 요약, 환경 분리(anon key만 앱에 포함, service key는 서버 전용, `.env.example`로
형식만 커밋), 마이그레이션/RLS 개요(백엔드 미채택이면 "해당 없음")를 적는다.

**가드레일 적용 여부**(§6 "비용 가드레일 적용 대상" 칸): 이 프로젝트가 `COST-GUARDRAILS.md`
체크리스트 6항목 + Supabase 대응 3항목을 **적용해야 하는지**만 판정해 적는다(예: "전체 6항목 +
Supabase 대응 3항목 적용" / "해당 없음(백엔드 미채택)"). **`COST-GUARDRAILS.md` 파일 자체를
채우고 `pipeline.json`의 `artifacts.guardrails`를 등록하는 것은 5단계(개발) 완료 시점의 몫이다**
— estimate는 적용 여부·범위를 판정할 뿐, 그 체크리스트 문서를 만들거나 항목별 준수 여부를
기록하지 않는다.

## PRD 갱신 (기능·화면 조정이 있을 때)

이번 조정으로 PRD §3(기능 목록)·§4(화면 목록)·§8(백엔드 결정 트리 결과)이 바뀌면, estimate가
**직접** `docs/PRD.md`를 수정한다:

- `docs/PRD.md`도 다른 모든 산출물과 동일한 표준 절차를 따른다(예외 없음): ① Read로 현재
  `docs/PRD.md` 전체를 읽는다 ② **바뀐 부분만**(해당 §3 행, §4 행과 화면별 유저 스토리, §8 백엔드
  결정 트리 결과 칸) 메모리 상에서 고치고 나머지는 읽은 그대로 유지한다 — 문서 전체를 새로
  작성하지 않되 반영은 전체 내용으로 한다 ③ Write 도구로 `docs/PRD.md.tmp`에 그 전체 내용을 쓴다
  ④ `bash .claude/atomic-mv.sh docs/PRD.md.tmp docs/PRD.md`로 교체한다. (artifact_get 등은 상태와
  무관하게 즉시 파일을 읽으므로, 부분 수정을 파일에 직접 반영하면 찢긴 읽기 창이 실제로 발생할 수
  있다 — 이 문서에 별도 예외를 두지 않는다.)
- §3 WON'T 행 이유 필수, §4 화면 ID kebab 규칙, §8 applicationId 불변 등 PRD 자체의 템플릿 규칙은
  수정 후에도 그대로 지킨다.
- 화면 목록이 바뀌었으면 §4 표와 "화면별 유저 스토리·수용 기준" 절을 함께 동기화한다(표에 없는
  화면의 유저 스토리 절만 남기거나, 화면은 있는데 유저 스토리 절이 없는 불일치를 만들지 않는다).

## §7 PRD diff 요약 (재승인 게이트)

- 조정이 전혀 없었으면: "해당 없음 — PRD 대비 기능 가감 없음"이라고 적는다.
- 조정이 있었으면: 변경 대상(예: "§3 기능 목록 — MUST 기능 X", "§4 화면 목록 — `stats-detail`
  삭제", "§8 백엔드 결정 트리 결과") · 변경 전(기준 PRD 버전 명시) · 변경 후 · 사유를 표로 채운다.
  이 표가 비어 있으면 안 된다 — 이번 ESTIMATE.md에 대한 사용자 컨펌은 **곧 이 표에 적힌 PRD
  변경사항의 재승인**으로 정의되므로(무통지 변경 금지), 실제로 고친 내용을 빠짐없이 반영한다.

## 완료 처리

1. 메타(slug/버전/상태/기준 PRD 버전/조정 회차) + §1~§7 8블록이 모두 채워졌는지(해당 없음 사유
   포함) 점검한다.
2. §1 최종 판정과 PRD §8이 일치하는지, 불일치했다면 PRD §8을 갱신하고 §7에 반영했는지 확인한다.
3. 백엔드 채택 시 §3 각 행에 산식+완화책+완화 후 예상치가 모두 채워졌는지, §4에 3개 시나리오가
   있는지 확인한다.
4. `pipeline.json`에 원자적으로 기록: `artifacts.estimate = "ESTIMATE.md"`(기존 `ideas`/`prd`/
   `mockup` 등 다른 키 보존), `stageStatus: "awaiting_confirm"`.
5. 채팅으로 요약 보고: 백엔드 최종 판정(로컬/정적/백엔드+스택), 백엔드 채택 시 MAU 시나리오별
   예상 월 비용 한 줄씩, 이번 조정으로 PRD가 바뀌었는지(바뀌었다면 §7 diff 한 줄 요약), **화면
   목록에 영향이 있었다면 "목업 롤백을 권장합니다 — 영향받은 화면: `<화면ID, ...>`" 문구를
   반드시 포함**, 그리고 "컨펌하면 5단계(개발)로 진행합니다(이번 조정으로 PRD가 바뀌었다면
   컨펌은 그 변경에 대한 재승인입니다)"라는 다음 행동 안내. 보고는 비개발자 눈높이로 쓴다 —
   전문용어는 풀어 쓰고, 표의 숫자에는 뜻을 한 줄로 덧붙인다(계약 7항).
