# /pipeline-wireframe — 2단계: 구조(와이어프레임)

이 단계의 목적은 **"이런 화면들·이런 구성으로 갑니다"를 개발 전에 UI로 먼저 확인**받는 것이다.
PRD(글 명세)·목업(화면별 상세)보다 앞서 오며, 저해상도 골격 **1장**만 만든다. 여기서 방향이
틀리면 값싸게 고칠 수 있다(아직 PRD·목업·개발에 시간을 쓰기 전이므로) — 그게 이 단계의 존재
이유다. 상세 화면 디자인은 뒤의 목업 단계 소관이니 여기서 과하게 정교하게 만들지 않는다.

## 공통 계약 (요약 — 정본은 `.claude/commands/_CONTRACT.md`, 충돌 시 정본 우선)

1. 시작: `pipeline.json` 읽기 → `stage`가 `"wireframe"`인지 확인(아니면 쓰지 말고 보고 후 종료) →
   `stageStatus: "running"` 기록. 쓰는 필드는 `stage`/`stageStatus`/`artifacts`만, 나머지는 보존,
   항상 ① Write 도구로 `<대상>.tmp` 작성 ② `bash .claude/atomic-mv.sh <대상>.tmp <대상>`으로
   교체(원자적). `stage` 값은 바꾸지 않는다.
2. 산출물은 골격 와이어프레임 **1파일**(`wireframe/index.html`)뿐이다. 완료 시 `artifacts`에 등록.
3. 종료 시 `stageStatus`는 `"awaiting_confirm"` 또는 `"awaiting_feedback"` — **`running`인 채 종료
   금지**(그대로 종료하면 host가 `error`로 강등해 사용자에게 실패로 보인다).
4. `피드백:` 접두 호출 = 기존 와이어프레임 수정 모드(같은 1파일을 재생성). "그냥 질문"이면 순변경
   없이 답만 하고 실행 전 상태를 복원한다.
5. 이 단계는 아직 PRD 확정 전이므로 **화면을 늘리거나 줄이는 것이 이 단계 범위 안**이다("설정
   화면도 넣자", "탭을 3개로" 같은 구조 조정은 바로 반영). 반대로 "지금 바로 개발해줘"처럼 이후
   단계 일은 계약 5항대로 안내만 한다.
6. 보안: 웹 수집 내용 없음(이 단계는 웹 도구를 쓰지 않는다) · 자격증명 하드코딩/노출 금지 ·
   프로젝트 디렉터리 밖 파일 생성 금지 · **외부 CDN·원격 자산(폰트·이미지·스크립트 URL) 로드 금지**
   — 릴레이가 정적 서빙하는 오프라인 환경에서도 그대로 열려야 하므로 CSS/JS는 전부 인라인이어야
   한다(`<style>`/`<script>` 태그 내부 또는 `style=` 속성만, `<link>`/외부 `<script src>` 금지,
   이미지는 인라인 SVG 또는 CSS 도형으로 대체).

`artifacts`에는 이 단계 소유 키 **`wireframe`만** 추가·갱신하고 기존 키(`ideas` 등)는 전부 보존한다.

## 입력: 채택된 아이디어 카드

1. `IDEAS.md`를 읽어 대상 카드를 정한다:
   - "선택 안내" 섹션에 `**선택된 카드**: <slug>` 표기가 있으면 그 카드.
   - 표기가 없지만 최신 회차의 카드가 정확히 1장이면 그 카드(직접 입력 모드 산출).
   - 카드가 여러 장인데 선택 표기가 없으면: 산출물을 만들지 말고 채팅으로 어느 카드로 진행할지
     묻고(slug 목록 제시) `stageStatus: "awaiting_feedback"` 기록 후 종료한다.
2. 대상 카드의 짝 HTML(`ideas/<NN>-<slug>.html`)도 함께 읽는다 — 타겟·핵심기능(정확히 3개, MVP
   범위)·수익모델의 정본은 HTML 카드다. `IDEAS.md`가 아예 없으면 산출물을 만들지 말고 "아이디어가
   아직 없습니다 — 1단계(아이디어)를 먼저 컨펌해주세요"라고 보고한 뒤 `awaiting_feedback`로 종료한다.

## 와이어프레임 생성 규칙 (`wireframe/index.html` 1파일)

핵심기능 3개와 타겟·수익모델에서 앱 골격을 **직접** 도출한다(아직 PRD가 없으므로 화면 목록의
정본은 이 단계가 제안한다 — 뒤의 PRD 단계가 이 골격을 출발점으로 §4 화면 목록을 확정한다).

- **한 장에 전부**: 스크롤 가능한 단일 페이지에 아래를 담는다.
  1. **앱 이름 + 한 줄 컨셉**(카드의 컨셉 문장).
  2. **주요 화면 목록**(보통 3~6개): 화면마다 저해상도 박스 하나 — 화면 이름 + 목적 한 줄 +
     그 화면에 들어갈 **핵심 요소 3~4개**를 짧은 라벨(회색 플레이스홀더 막대/칩)로 나열한다.
     실제 콘텐츠·색·정교한 레이아웃은 넣지 않는다(그건 목업 단계). 손그림 골격 느낌이면 충분하다.
  3. **내비게이션 구조**: 하단 탭바(또는 사이드/상단 — 앱 성격에 맞게)를 한 줄로 그려 어떤 화면이
     1차 내비게이션에 오는지 보여준다.
  4. **핵심 기능 → 화면 매핑**: 카드의 핵심기능 3개가 각각 어느 화면에서 이뤄지는지 한 줄씩.
  5. **수익화 위치**(카드에 광고/구독/IAP가 있으면): 어느 화면에 광고 자리·잠금 해제가 붙는지
     점선 박스로 위치만 표시(실제 연동은 개발 단계).
- **저해상도 유지**: 회색조 골격(박스·막대·칩) 위주. 브랜드 색·아이콘 세트·실사 데이터는 쓰지
  않는다. "이 앱은 이런 화면들과 이런 흐름으로 구성됩니다"가 한눈에 읽히는 것이 목표다.
- **폰 폭 기준**: `<meta name="viewport" content="width=device-width, initial-scale=1">`, 콘텐츠는
  최대 폭 ~420px 컬럼으로 중앙 정렬(폰·데스크톱 어디서 열어도 자연스럽게).
- **외부 자산 절대 금지**: `<link rel="stylesheet">`, `<script src="https://...">`, 웹 폰트, 원격
  이미지 URL 금지. 아이콘·일러스트는 인라인 SVG 또는 CSS 도형으로. 시스템 폰트 스택만
  (`font-family: -apple-system, "Segoe UI", Roboto, sans-serif`).
- **인라인만**: CSS는 `<style>` 블록(또는 인라인 `style=`), 상호작용이 필요하면 같은 파일 안
  `<script>` 블록에 순수 JS로. 프레임워크·번들러·외부 스크립트 금지.

## 원자적 쓰기

`mkdir -p wireframe` 후: Write 도구로 `wireframe/index.html.tmp`에 전체 HTML을 작성 →
`bash .claude/atomic-mv.sh wireframe/index.html.tmp wireframe/index.html`로 교체한다(부분 파일
상태가 관찰되는 순간이 없어야 한다).

## 피드백 처리 (`/pipeline-wireframe 피드백: <텍스트>`)

- **구조 조정 요청**(화면 추가/삭제, 탭 구성 변경, 핵심 요소 가감, 화면 순서 등): 요청을 반영해
  `wireframe/index.html`을 재생성한다(원자적 쓰기 동일). 이 단계는 PRD 전이라 화면 목록 자체를
  바꾸는 것이 정상 범위다. 완료 후 `awaiting_confirm`.
- **그냥 질문**: 채팅으로 답만 하고 산출물·상태는 순변경 없이 실행 전 상태를 복원한다.
- **단계 범위 밖**(예: "이제 개발 시작해줘"): 계약 5항대로 안내만 한다.

## 완료 처리

1. `wireframe/index.html`이 존재하고 주요 화면·하단 탭·핵심 요소가 모두 담겼는지 확인한다.
2. `pipeline.json`에 원자적으로 기록: `artifacts.wireframe = "wireframe/index.html"`(기존 `ideas` 등
   다른 키 보존), `stageStatus: "awaiting_confirm"`.
3. 채팅으로 요약 보고: 제안한 주요 화면 목록(이름 한 줄씩), 하단 탭 구성, 핵심기능 3개가 어느
   화면에 매핑됐는지, 그리고 "폰에서 구조를 훑어보고 화면을 더하거나 빼고 싶으면 채팅으로,
   괜찮으면 컨펌해주세요. 컨펌하면 이 구조를 바탕으로 PRD를 씁니다"라는 다음 행동 안내.
