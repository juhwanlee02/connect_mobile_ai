# /pipeline-test — 6단계: 테스트 (웹 미리보기)

## 공통 계약 (요약 — 정본은 `.claude/commands/_CONTRACT.md`, 충돌 시 정본 우선)

1. 시작: `pipeline.json` 읽기 → `stage`가 `"test"`인지 확인(아니면 쓰지 말고 보고 후 종료) →
   `stageStatus: "running"` 기록. 쓰는 필드는 `stage`/`stageStatus`/`artifacts`만, 나머지는 보존,
   항상 ① Write 도구로 `<대상>.tmp` 작성 ② `bash .claude/atomic-mv.sh <대상>.tmp <대상>`으로
   교체(원자적 — `pipeline.json`에 적용. `preview/`의 빌드 산출물은 flutter가 생성한 파일을
   복사하는 것이라 이 절차 대상이 아니다). `stage` 값은 바꾸지 않는다.
2. 산출물 = `preview/`(웹 빌드 산출물 사본 — 별도 템플릿 없음, 빌드 결과 그대로). 완료 시
   `artifacts`에 등록.
3. 종료 시 `stageStatus`는 `"awaiting_confirm"` 또는 `"awaiting_feedback"` — **`running`인 채 종료
   금지**(그대로 종료하면 host가 `error`로 강등해 사용자에게 실패로 보인다).
4. `피드백:` 접두 호출 = 수정 모드(아래 "피드백 분류"). "그냥 질문"이면 순변경 없이 답만 하고
   실행 전 상태를 복원.
5. **피드백 분류 규칙(계약 5항)**: 버그·문구·스타일 수정은 이 단계 안에서 반복 처리한다. **작은
   기능 추가·변경**(기존 화면 안 요소·동작 수준)도 바로 반영하되 `docs/PRD.md` §3·§4를 함께
   갱신한다(문서와 앱이 어긋난 채 배포되는 것 방지). **큰 방향 전환**(새 화면 여러 개·수익모델·
   백엔드 변경)만 산출물을 바꾸지 말고 되돌리기(롤백)를 권한다.
6. 보안: 이 단계는 웹 도구를 쓰지 않는다(신뢰불가 웹 입력 해당 없음) · 자격증명·API 키
   하드코딩·노출 금지 · 프로젝트 디렉터리 밖 파일 생성 금지(`preview/`는 프로젝트 안이다).

`artifacts`에는 이 단계 소유 키 **`preview`만** 추가·갱신하고 기존 키(`ideas`/`prd`/`mockup`/
`estimate`/`app`/`guardrails` 등)는 전부 보존한다.

## 절차 (①~⑤ 번호 순서 강제)

**쉘 작업 디렉터리는 호출 간 유지된다.** `app/` 내부 명령은 **반드시 두 번의 개별 Bash 호출**로
나눠 실행한다 — ① `cd app && <명령>` ② 완료 후 별도 호출로 `cd ..` 복귀. **한 호출 안에 `cd`를
두 번 이상 넣거나(`cd app && <명령>; cd ..`처럼) 괄호 서브셸(`(cd app && <명령>)`)로 묶지 말 것**
— 런타임 승인 정책이 "한 명령 안의 다중 디렉터리 변경"과 "셸 연산자(괄호 등)"를 범주적으로 차단해
headless(`acceptEdits`) 실행에서 거부된다(Phase 5 Task 4 실측 — `.superpowers/sdd/task-4-report.md`).
아래 `cd app && <명령>` 표기는 ①만을 가리키며, 실행 후 잊지 말고 ②로 복귀할 것. 그 외 명령은 전부
프로젝트 루트 기준.

### ① 입력 확인

- `app/pubspec.yaml`이 존재하는지 확인한다(5단계 산출물, artifacts.app). 없으면 아무 산출물도
  만들지 않고 채팅으로 "앱이 아직 없습니다 — 5단계(개발)를 먼저 컨펌해주세요"라고 보고한 뒤
  `stageStatus: "awaiting_feedback"` 기록 후 종료한다.
- `pipeline.json`의 `project` 값을 읽어 둔다 — 아래 `--base-href`의 `<프로젝트명>`이다.
- `docs/PRD.md` §6(수익화)·§10(네이티브 필요 요건)을 읽어 둔다 — ⑤ "web 검증 불가 목록"의
  근거다.

### ② 웹 릴리즈 빌드 (서브패스 서빙 3조치 + 데모 시드 — 스펙 §2-6)

실행: `cd app && flutter build web --release --base-href=/preview/<프로젝트명>/preview/ --pwa-strategy=none --dart-define=SEED=true`
(완료 후 별도 호출로 `cd ..` 복귀)

3조치 + 시드 플래그의 의미(왜 이 플래그들이 필수인가):

0. **`--dart-define=SEED=true`** — 미리보기가 **빈 화면으로 보이지 않도록** develop이 채운
   `seedDemoData()`(`lib/seed.dart`)를 켜서 대표 샘플 데이터가 미리 채워진 상태로 보여준다. 이 값이
   없으면 갓 설치한 빈 앱이 떠서 "이게 맞는지" 판단이 어렵다. **실제 스토어 빌드(릴리즈)는 이 플래그를
   쓰지 않으므로 프로덕션은 빈 상태로 시작**한다 — 미리보기 전용 조치다.

1. **`--base-href=/preview/<프로젝트명>/preview/`** — 미리보기는 릴레이의 서브패스
   `/preview/<프로젝트명>/preview/`로 서빙되므로, 이 값이 없으면 JS·폰트 등 자산 요청이 전부
   404가 된다. 값은 반드시 슬래시로 시작하고 끝나야 하며 `<프로젝트명>`은 `pipeline.json`의
   `project` 값 그대로다.
2. **MIME 타입(`.wasm`/`.otf`/`.ttf` 등)** — 릴레이 쪽 MIME 맵이 처리한다. 스킬이 할 조치는
   없다(정보로만 인지).
3. **`--pwa-strategy=none`** — 결과물 앱이 폰 컨트롤 앱과 같은 origin에서 서빙되므로, service
   worker가 등록되면 컨트롤 앱과 캐시 간섭을 일으킨다. 반드시 끈다.

빌드가 실패하면 `app/` 소스를 고쳐 재빌드한다(Read로 읽고 Edit으로 해당 부분을 수정하거나 —
필요하면 Write로 해당 파일 전체를 다시 쓴다). 고칠 수 없으면 실패 로그를 요약해 채팅으로 보고하고
`stageStatus: "awaiting_feedback"`을 기록한다.

### ③ `preview/`로 복사 (기존 내용 교체)

1. `mkdir -p preview`
2. `cp -R app/build/web/. preview/` — 기존 미리보기가 있으면 동일 경로 파일이 새 빌드로
   덮어써져 교체된다(빌드 산출물의 진입 파일명은 고정이라 덮어쓰기로 충분하다).

### ④ 상태·산출물 기록

`pipeline.json`에 원자적으로 기록: `artifacts.preview = "preview/index.html"`(기존 키 전부 보존),
`stageStatus: "awaiting_confirm"`.

### ⑤ 채팅 보고 — web 검증 불가 목록 필수

1. "미리보기 준비 완료 — 폰에서 실제 앱을 직접 조작해보세요"와 함께 빌드 요약(성공 여부, 재빌드
   회차)을 보고한다. **미리보기는 `SEED=true`로 빌드돼 예시(데모) 데이터가 채워진 상태**임을 한 줄
   덧붙인다 — "보이는 목록·수치는 화면 확인용 예시이고, 실제 설치 앱은 빈 상태로 시작합니다"라고
   안내한다(빈 화면 오해 방지). 앱에 도메인 데이터가 없어 시드가 스텁이면 그 사실을 대신 적는다.
2. **web 검증 불가 목록**: PRD §6·§10에서 **채택된 기능 기준**으로, 이 미리보기 URL에서 검증할
   수 없는 항목을 나열한다 — 각 항목마다 **"실기기에서만 확인 가능"**을 명시한다:
   - 광고(AdMob — 전면/보상형): web에서 동작하지 않음, 자리표시 UI로 대체됨 — 실기기에서만
     확인 가능
   - 푸시 알림: 실기기에서만 확인 가능
   - 인앱결제·구독: 실기기에서만 확인 가능
   - PRD §10의 네이티브 요건 각각(예: 위젯, 백그라운드 작업): 실기기에서만 확인 가능
   해당 기능이 하나도 없으면 "web에서 검증 불가한 채택 기능 없음"이라고 적는다(목록 항목 자체를
   생략하지 않는다). 실기기 검증은 릴리즈 후 스토어 내부 테스트 트랙에서 이뤄진다는 것도 한 줄
   덧붙인다.
3. 다음 행동 안내: "버그·문구·스타일 피드백은 이 단계에서 바로 수정합니다. 컨펌하면 7단계
   (릴리즈 패키지)로 진행합니다."

## 피드백 처리 (`/pipeline-test 피드백: <텍스트>`) — 분류 규칙(계약 5항)

- **버그·문구·스타일 수정**: `app/` 소스를 수정(Read → Edit로 해당 부분 수정, 필요하면 Write로
  전체 재작성)한 뒤 **①~③을 재실행**(재빌드 + `preview/` 재복사 — 재빌드가 컴파일 게이트를
  겸한다)하고 `awaiting_confirm`을 기록한다. 수정→재빌드 루프는 이 단계 안에서 몇 번이든
  반복한다.
- **작은 기능 추가·변경**(기존 화면 안 요소·동작 수준 — 계약 5항의 "작은 변경" 기준): 바로
  반영한다 — `app/` 수정 → `docs/PRD.md` §3·§4의 해당 부분도 함께 갱신(원자적 쓰기) →
  **①~③ 재실행** → `awaiting_confirm`.
- **큰 방향 전환**(새 화면 여러 개, 수익모델·백엔드 변경, 화면 구조 개편): 산출물을 바꾸지 말고
  "큰 변경이라 PRD부터 다시 정리하는 게 안전해요 — 되돌리기(롤백)를 권합니다"라고 안내한다.
- **그냥 질문**(설명 요청·상담): 채팅으로 답만 하고 산출물·상태는 순변경 없이 실행 전
  상태(보통 `awaiting_confirm`)를 복원한다.
